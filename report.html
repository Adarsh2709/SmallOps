1. Project Title & Objectives

1.1 Project Title

smallOps: Autonomous Prompt-to-Cloud Serverless Application Engine

1.2 Project Objectives

  • Democratize Cloud Deployment: Enable non-technical users and developers to translate natural language prompts into live, secure, production-grade cloud applications within 15–30 seconds.
  • Serverless-First AWS Architecture: Leverage AWS serverless primitives (AWS Lambda, Amazon DynamoDB, Amazon S3, Amazon CloudFront) to achieve zero idle cost, high availability, and auto-scaling.
  • Out-of-the-Box Security & Identity: Implement zero-configuration enterprise authentication and role-based access control (Viewer and Editor) using Amazon Cognito and AWS IAM.
  • Immutable Decision Traceability: Maintain an immutable audit graph of all agent decisions, code diffs, and deployment snapshots using DynamoDB Single-Table Design, enabling deterministic one-click rollbacks.
  • Autonomous Self-Healing: Implement autonomous maintenance routines using Amazon Bedrock to monitor application health, analyze runtime errors, and deploy verified fixes without human intervention.

2. Introduction & Problem Statement

2.1 The Problem

Modern generative AI models can write functional application code in seconds. However, turning generated code into software that a team can reliably use still requires significant DevOps knowledge:

  • Manual cloud infrastructure provisioning (VPCs, subnets, route tables, security groups).
  • Setting up user authentication, session tokens, and role-based access.
  • Configuring databases and persistent object storage.
  • Secure distribution via HTTPS domains without emailing raw source zip files.
  • Preventing regression breaks during iterative maintenance and bug repairs.

Traditional cloud platforms are built for large-scale enterprise microservices, which introduces significant setup friction for lightweight internal tools, prototypes, and departmental utilities.

2.2 Proposed Solution

smallOps provides an opinionated cloud platform designed specifically for small software running natively on AWS. Through natural language prompting, the platform clarifies ambiguities upfront, generates verified Python/FastAPI code, provisions serverless AWS resources on demand, secures the deployment with Amazon Cognito, and provides continuous health monitoring with automated rollback capabilities.

4. System Architecture & Workflow

4.1 High-Level Architecture Diagram

+------------------------------------+ | Client Browser / User | +-----------------+------------------+ | HTTPS / DNS +-----------------v------------------+ | Amazon CloudFront | +--------+------------------+--------+ | | Static Assets | | API & Dynamic Traffic +--------v-------+ +-------v--------+ | Amazon S3 | | AWS Lambda / | | (Frontend App) | | Function URL | +----------------+ +-------+--------+ | +--------------------------------+-------------------------------+ | | | +-------v--------+ +--------v----------+ +--------v--------+ | Amazon Bedrock | | Amazon DynamoDB | | Amazon Cognito | | (Claude 3.5) | | (Single-Table DB) | | (Auth & RBAC) | +----------------+ +-------------------+ +-----------------+ | | | Clarify & Codegen Timeline & State Tokens & Magic Links

4.2 Operational Workflow

  1. Prompt Intake & Ambiguity Clarification: User submits an app description. smallOps evaluates requirements with Bedrock and poses up to 3 focused clarification questions with recommended defaults.
  2. Code Synthesis & Sandbox Verification: Bedrock generates runnable code; an isolated verifier validates imports, syntax, and runs smoke checks.
  3. Instant Cloud Deployment: Single-file apps are deployed to AWS Lambda with an HTTPS Function URL; multi-file apps deploy to AWS Fargate.
  4. Audit Logging: All execution steps, prompts, and diffs are committed to DynamoDB.
  5. Autonomous Self-Healing: Health probes continuously monitor live endpoints; on failure, Bedrock diagnoses root causes and deploys verified patches automatically.

7. Challenges Faced & Solutions Implemented

Challenge Faced Impact Engineering Solution
LLM Non-Determinism Generated responses occasionally included markdown backticks or extra text, failing automated deployments. Used Amazon Bedrock Converse API with strict Pydantic schemas and AST syntax sanitizers before deployment.
Serverless Cold Starts First requests to new Lambda functions experienced latency spikes of 2 to 3 seconds. Stripped heavy dependencies, pre-compiled wheels, and minimized package bundle size to under 15MB.
Self-Healing Looping Continuous repair cycles could potentially loop infinitely on unsolvable logic errors and drain API quotas. Enforced a hard ceiling of 2 repair attempts per cycle and implemented DynamoDB concurrency locks.
CORS Restrictions Browser blocked cross-origin requests between the S3/CloudFront domain and the Lambda Function URL. Configured CloudFront response headers policy and explicit CORS settings on the Lambda Function URL.

8. Resource Cleanup & Cost Optimization

Assessment Compliance Note: In accordance with project instructions, all active resources were audited and teardown procedures verified to avoid ongoing charges on the AWS account.

To safely terminate and remove unused AWS resources, execute the following:

  1. Automated CDK Teardown: Run cd infra && npx cdk destroy --all to delete the provisioned CloudFormation stacks.
  2. S3 Buckets: Empty all objects in the bucket before deletion (S3 → Select Bucket → Empty → Delete).
  3. DynamoDB Tables: Select the table in the console and click Delete table.
  4. CloudFront: Select distribution, click Disable, and once disabled, click Delete.
  5. Lambda Functions: Select generated functions under Actions → Delete.
